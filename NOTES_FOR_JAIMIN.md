- 2026-09-20: **Research for dry-day-v3: what the regulators and the literature actually do.** Jaimin asked not to eyeball the thresholds. Findings, all quoted and dated in `06_SOURCES.md` §27–30:
  - **The EA has published no method.** Its blog says only that it gathers "rainfall data from local rain gauges as well as rainfall radar information" and then investigates site by site, checking "the accuracy of certain rainfall monitors and drain down times". So the EA does exactly what v3 proposes — it does not trust a single gauge reading — but it has not written down how.
  - **SOAF 2025 (EA) sets no rainfall-gauge rule at all** — it treats rainfall only as the "exceptional rainfall" screen. Recorded as a negative finding so it is not researched again.
  - **The nearest thing to an official rule is Welsh, not English.** NRW's GN066 (v1.0, 26 Oct 2023) says for the dry-day test: "Use rain gauge data that is the most representative for the SO. Where there is no nearby rain gauge, the three closest gauges can be triangulated. Radar data can be used where the approach is agreed with us." No distance in kilometres appears anywhere in it. Two things follow: **three** closest gauges is a regulator-sanctioned minimum for combining gauges, and radar substituting for unrepresentative gauge data is explicitly contemplated.
  - **Worth knowing:** GN066 also allows "one dry day" after rainfall ends for network drain-down before a discharge counts. The EA's blog definition, which this site implements, does not. Our rule is therefore stricter than the Welsh classification test on that point. Not a reason to change anything — §5 stays as specified — but the Method page should say it.
  - **Peer-reviewed precedent for the radar test we already have:** RainGaugeQC (Ośródka et al., AMT 15, 5581–5597, 2022) compares any gauge reading below a small threshold against radar "at the gauge location and its surrounding of 3×3 pixels (the pixel size is 1 km × 1 km)" and, if radar is above a threshold, treats the gauge's "no precipitation" as false and sets its quality to zero. That is the same 3×3 one-kilometre box `radar.py` already samples, which means our radar column is the right shape for this job by accident of following the ODIM grid.
  - **Peer-reviewed precedent for the neighbour test:** the Faulty Zero filter of de Vos et al. (2019), the standard in crowdsourced-rainfall QC, flags a station when the **median** of neighbours within **10 km** (at least **5** neighbours) is above zero for at least **6** consecutive intervals while the station reports zero. Note *median*, not "two neighbours above a threshold" — the median is what makes it robust to one unrepresentative neighbour, and v2's "at least two gauges" test is the cruder form.
  - **Why the published numbers cannot be copied across unchanged.** de Vos's 10 km / 5 neighbours comes from a Dutch city with hundreds of amateur stations. England has roughly 1,000 EA gauges for 130,000 km², a mean spacing near 13 km, so "5 neighbours within 10 km" would almost never fire here. The radius has to come from our own network, not from theirs.
  - **Proposal, to be calibrated rather than guessed:** keep the 10.0 km candidate radius (§5.3); for each window, compare the chosen gauge against the **median of every complete-window gauge within R km, requiring at least 3 of them** (GN066's three-gauge minimum, de Vos's median), and against the radar 3×3 box (RainGaugeQC's construct). Then pick R and the mm threshold **empirically**: radar gives an independent referee for every event since 21 Nov 2024, so we can plot how often the neighbour test and the radar agree as R and the threshold vary, and choose the pair that maximises agreement while keeping the convective-shower false-positive rate measurable. That produces a defensible number instead of a plausible one, and the whole curve can go on the Method page.

- 2026-09-20: **Jaimin's decision on poll frequency: use an external trigger, not another GitHub trick.** His reasoning: we have already been clever with GitHub several times. Chosen service **cron-job.org** — free ("Our service is absolutely free and financed entirely by voluntary donations"), runs up to once per minute, and lets you set the request method, headers and body, which a GitHub API call needs. It does require an email signup.
  Setup, verified against the live API from this machine (a dispatch returns **HTTP 204 No Content**, not the 200 the docs page summarises):
  1. GitHub → Settings → Developer settings → **Personal access tokens → Fine-grained tokens** → Generate new token. Name `cron-job.org poll trigger`; resource owner `jmshah8`; repository access **Only select repositories → storm-water-tracker**; permissions **Repository permissions → Actions → Read and write** (Metadata read-only is added automatically). **Expiry: none.** GitHub allows it for fine-grained tokens ("Infinite lifetimes are allowed but may be blocked by a maximum lifetime policy set by your organization or enterprise owner" — no such policy on a personal account), and an expiring token fails in the worst way: it dies quietly and polling stops with no signal but a stale footer. The blast radius is small enough to justify it — the token can only start and cancel workflows in one public repo — and it can be revoked from GitHub settings at any time. GitHub deletes tokens unused for a year, which cannot happen to one firing every ten minutes. Copy the token once.
  2. cron-job.org → sign up, verify the email, **Create cronjob**.
  3. URL `https://api.github.com/repos/jmshah8/storm-water-tracker/actions/workflows/poll.yml/dispatches`; schedule every 10 minutes; request method **POST**.
  4. Headers: `Accept: application/vnd.github+json`, `Authorization: Bearer <token>`, `X-GitHub-Api-Version: 2022-11-28`, `Content-Type: application/json`. Body: `{"ref":"main"}`.
  5. Turn on the failure notification, save, and use **Test run**: it should report 204 and a new `poll` run should appear in Actions within seconds.
  **The token never goes in this repository** — acceptance item E1 greps for exactly that mistake. Worst case if cron-job.org were breached: someone could start, cancel or re-run workflows in this one repo. They could not push code or read anything private, because the repository is public and the token grants no contents permission.

The six-polls-per-run design (17 Sep) exists only because GitHub would not start the job often enough; with a reliable external trigger every ten minutes, a run that holds the lane for 50 minutes would make every new trigger queue behind it and cancel the previous pending run. One poll per run, with GitHub's own `*/10` schedule left in place as a fallback, is the right shape then.
