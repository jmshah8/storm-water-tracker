# 04 — Phase 3 build plan: Thames Water history back-test (April 2022 →)

Start only after Phase 2 is `done`. Purpose: the Hub has no history, but Thames Water's own API reportedly exposes a per-event alert stream back to 1 April 2022. Pulling it and running it through the *unchanged* `dry-day-v1` rule gives a multi-year view for one company — a back-test of the method on data we did not collect ourselves.

Two cautions, to be written on the back-test page: (1) the API details in `01_SPEC.md` §2.6 come from two open-source clients, not from Thames's documentation — step 3.1 confirms them; (2) these are the company's own alerts, unaudited, exactly like the Hub feed.

- [x] **3.1 Confirm the API contract.** Write `scripts/thames_history.py probe`. Using headers `client_id`/`client_secret`: (a) `GET {base}/DischargeCurrentStatus?limit=5` → print status code, top-level keys, and the first item's field names and values; (b) `GET {base}/DischargeAlerts?limit=5&col_1=DateTime&operand_1=gte&value_1=2022-04-01` → same; (c) test pagination: try `offset=1000` (or `col_2=DateTime&operand_2=lt&value_2=...` windowing if `offset` is not honoured) and confirm you can walk the full stream without gaps or duplicates; (d) request alerts with `value_1=2021-01-01` and record the earliest `DateTime` actually returned.
  (e) **Timezone of `DateTime`:** fetch alerts for the last 7 days, pair each alert location with the nearest Thames Hub overflow within 100 m using a throwaway coordinate match (the proper mapping is built in 3.3 — do not depend on it here), then test offsets of 0, +60 and −60 minutes against the Hub events' start times; the correct offset matches within a few minutes for the large majority. If the API returns an explicit zone marker (`Z` or `+01:00`), record that instead.
  **CHECK 3.1:** paste field names for both endpoints; state the working pagination method; state the earliest alert date; state the timezone finding with the match counts per offset. Write all of it into `NOTES_FOR_JAIMIN.md` under "Thames API contract ({date})". - [x] **3.3 Convert alerts to events and map locations to Hub overflows.**
  - Pair each `Start` alert with the next `Stop` alert for the same location → an event with `start_utc` (converted to UTC using the 3.1(e) finding), `end_utc`, `duration_min`, `source = thames_api`, `end_observed = true`. A `Start` followed by another `Start` without a `Stop` → close the first at the second's start with `end_observed = false`. Offline start/stop → `data/thames_history/offline_pre_launch.csv` (same columns as `data/offline/*.csv` plus `source`), not into `data/offline/`.
  - **Avoid double-counting the seeded Hub events.** At launch the Hub gave us the *latest* pre-launch event for every Thames overflow, already in `data/events/`. Any `thames_api` event for the same `overflow_key` whose `start_utc` is within ±15 minutes of an existing Hub event is dropped from `events_pre_launch.csv` (the Hub row wins; count the drops in the report). This keeps `event_id` unique across all event files (acceptance B2/A7).
  - Map each API location to an `overflow_key`: first try an exact match between the API's location identifier(s) (e.g. `LocationName`, `PermitNumber` if present) and the Hub `Id` for Thames; otherwise convert the API `X`,`Y` (OSGB36 easting/northing, EPSG:27700 — confirm from the probe values, which should be six/seven-digit metres) to WGS84 with `pyproj` and match the nearest Thames Hub overflow within 100 m. Unmatched → create `overflow_key = thames:TWAPI:{LocationName}` with the API coordinates.
  - Write `data/thames_history/events_pre_launch.csv` (same columns as `data/events/*.csv`) covering starts **before** `launch_utc` (from 1 April 2022 up to the launch date — this includes 2025 and the months of 2026 before launch); write the overlap period (starts at/after `launch_utc`) to `data/thames_history/events_overlap.csv` for validation only.
  - **Extend `scripts/classify.py`** to load `data/thames_history/events_pre_launch.csv` in addition to `data/events/*.csv` (never `events_overlap.csv`), and `build_site.py` to include those events in the Thames company page and the back-test page (they are pre-launch, so they stay out of the site-wide period totals per the launch-date rule).
  **CHECK 3.3:** (a) mapping report: matched by ID, matched by coordinates, unmatched — expect ≥ 90% matched; list unmatched names; (b) **overlap validation**: for events in `events_overlap.csv`, find a Hub event for the same overflow with `start_utc` within ±15 minutes — report the match rate; **pass ≥ 90%** (same threshold as acceptance T3); below that → **GATE 3.3** (the mapping, the timezone or the API semantics are wrong); (c) number of `thames_api` events dropped as Hub duplicates; (d) `event_id` unique across `data/events/*.csv` + `events_pre_launch.csv`; (e) monthly event counts 2022-04 → launch, so gaps in the API history are visible. Commit: `step 3.3: thames events`.

- [x] **3.4 Historic rainfall.** Add a `--range START END` flag to `scripts/rain.py` (Phase 1 only had `--days`; `END` exclusive). Run it as the manual GitHub Actions workflow `thames-history.yml` → job `rain-backfill` with input `month` (`YYYY-MM`), which the job converts to `--range YYYY-MM-01 <first day of the following month>`; one month per run, so a failure loses at most a month. From 2022-03 to the launch month (autumn 2026) that is **about 55 months** × ~1,000 gauges ≈ 55,000 requests at ≤ 5/s — queue them with `gh workflow run thames-history.yml -f job=rain-backfill -f month=YYYY-MM`, a few at a time.
  **CHECK 3.4:** every day from 2022-03-31 to the day before launch has a daily file; per-year share of gauge-days with `n_readings ≥ 88` (report it — older data is usually more complete, not less); the gauge list used for history is the current `gauges.csv` (gauges opened after a date have no readings before it — that is expected and handled by gauge selection). Commit as each month lands.
