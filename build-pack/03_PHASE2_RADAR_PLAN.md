# 03 — Phase 2 build plan: Met Office radar as a second opinion

Start only after Phase 1 is `done`. Read `01_SPEC.md` §2.5 and §5 again. The radar **never changes a verdict** in this phase: the verdict stays gauge-based under `dry-day-v1`. Radar adds a second, independent rainfall estimate at the overflow's own location, shown beside the gauge evidence and used to label each dry-day flag as "radar agrees" or "radar disagrees". This is exactly how the EA describes its own method ("rainfall data from local rain gauges as well as rainfall radar information").

Add to `requirements.txt`: `h5py==3.*`, `numpy==2.*`, `pyproj==3.*`. No AWS SDK is needed: list a day with `GET https://met-office-radar-obs-data.s3.eu-west-2.amazonaws.com/?list-type=2&prefix=radar/YYYY/MM/DD/` (public XML listing, verified 15 Sep 2026) and download each key with a plain HTTPS GET of `https://met-office-radar-obs-data.s3.eu-west-2.amazonaws.com/{key}`.

- [x] **2.2 Write `swt/radar.py`.**
  - `load_frame(path) -> (rate_mm_per_h: np.ndarray float32 with NaN for nodata, meta)`: physical = raw × gain + offset; `nodata` → NaN; `undetect` → 0.0.
  - `accum_15min(rate) = rate / 4.0` (mm in 15 minutes).
  - `Grid` class built from `where` attributes: `pyproj.Transformer.from_crs("EPSG:4326", projdef, always_xy=True)` (**`always_xy=True` is essential** — without it pyproj expects lat,lon order and every point lands in the wrong place); `to_pixel(lat, lon) -> (row, col)` using the projected UL corner and `xscale`/`yscale` (row increases southward — verify against the corner attributes, do not assume); `in_bounds(row, col)`.
  - Unit tests with a synthetic 10×10 grid: gain/offset applied; nodata masked; undetect zero; a point at the UL corner maps to (0,0) and at the LR corner to (ysize−1, xsize−1).
  **CHECK 2.2:** `pytest -q` passes. Then a **geographic sanity check**: project London (51.5074, −0.1278), Manchester (53.4808, −2.2426), Newcastle (54.9783, −1.6178), Plymouth (50.3755, −4.1427), Norwich (52.6309, 1.2974): all `in_bounds`, and their relative positions (row/col ordering north→south, west→east) match geography. Print them. Commit: `step 2.2: radar reader`.

- [x] **2.3 Write `scripts/radar.py day DATE`.**
  For UTC day `DATE`: list keys under `radar/YYYY/MM/DD/`, download each (retry ×3), accumulate `total = Σ rate/4` and `max15 = max(rate/4)` grids, count frames present (expect 96). Then, for every overflow in `data/overflows.csv`: nearest pixel value of `total` and `max15`, and the maximum of `total` over the 3×3 pixel neighbourhood. Write `data/radar/daily/{DATE}.csv.gz` with columns `date, overflow_key, radar_total_mm, radar_max15_mm, radar_3x3_max_total_mm, n_frames, fetched_utc` (sorted by `overflow_key`; write to a temp file then rename). Skip `nodata` pixels (empty value, `n_frames` still recorded). Optional flag `--save-grid PATH` writes the two accumulated grids plus the `Grid` metadata to an `.npz` (git-ignored, under `.cache/`) for checks.
  Run it for a **wet day at least 4 days old** (pick, from `data/rain/daily/`, the most recent day ≥ 4 days ago on which ≥ 20 gauges recorded > 5 mm; gauge data that old is complete) with `--save-grid .cache/radar_{DATE}.npz`.
  **CHECK 2.3:** (a) `n_frames` is 96 (or report how many were missing and which); (b) file size ≤ 600 KB; (c) row count equals overflow count; (d) **radar-vs-gauge sanity**: `scripts/check.py --step 2.3 --grid .cache/radar_{DATE}.npz` takes the 20 gauges with the highest gauge `total_mm` that day and 20 gauges with zero, samples the saved radar `total` grid at each gauge's coordinates, and reports a rank correlation across the 40 points computed with numpy (rank both series, Pearson on the ranks — no scipy) and the median radar total for the zero-gauge group. **Pass: correlation > 0.6 and median < 1 mm** (the same thresholds as acceptance R3). Radar and gauges legitimately differ; this catches gross errors such as a wrong projection or gain. If it fails → **GATE 2.3**. Commit: `step 2.3: daily radar sampling`.
